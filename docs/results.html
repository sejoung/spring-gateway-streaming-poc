실패한 항목

MVC 기본 7번: 사용자가 중단해도 Backend가 멈추지 않음

무슨 일
클라이언트가 토큰 3개를 받고 연결을 끊어도, Backend는 남은 47개를 끝까지 만들고 정상 종료했습니다. 5회 모두 같았습니다.
왜
MVC Gateway는 클라이언트에 다음 토큰을 쓰려다 실패해야 끊긴 것을 압니다. 그 뒤 Backend 응답을 닫는데, Spring의 JDK 클라이언트는 닫을 때 연결 재사용을 위해 남은 응답을 끝까지 읽습니다(drain). 그래서 Backend는 클라이언트가 떠난 줄 모릅니다.
영향
실제 LLM이라면 사용자가 보지 않을 토큰 비용이 끝까지 나가고, 그동안 Tomcat 스레드와 Backend 연결이 하나씩 묶입니다.
해결
Jetty 클라이언트(spring.http.client.factory=jetty)는 drain하지 않고 바로 닫습니다. tuned에서 성공. 상세 과정은 부록의 T06.

MVC 기본 11·12번: 동시 스트림 200개를 넘으면 대기

무슨 일
요청은 모두 성공했지만, 201번째부터는 앞선 스트림이 끝날 때까지 첫 토큰을 받지 못했습니다. 500개 × 20초 스트림에서는 마지막 배치가 첫 토큰을 받기까지 40초 넘게 기다렸습니다.
왜
MVC Gateway는 스트림 하나가 Tomcat 스레드 하나를 스트림이 끝날 때까지 점유합니다. Tomcat 기본 최대 스레드는 200개입니다.
해결
가상 스레드(spring.threads.virtual.enabled=true)를 켜거나 server.tomcat.threads.max를 목표 동시 스트림 수 이상으로 늘립니다. tuned에서 성공.

MVC 기본 13번: k6 500 VU에서 1회 연결 실패

무슨 일
5회 실행 중 첫 1회에서 1,000건 중 77건이 연결 실패했습니다. 이후 4회는 모두 성공했습니다.
왜
재현되지 않았고 원인을 확인하지 못했습니다. 11번과 같은 스레드 부족 상태에서 연결이 몰린 것과 관련 있을 수 있지만 검증하지 않았습니다.

MVC 기본 · tuned 9번: 스트림 중간 오류를 클라이언트가 오류로 알 수 없음

무슨 일
Backend가 토큰 5개를 보낸 뒤 오류로 스트림을 끊었을 때, Backend 직접 호출과 WebFlux에서는 클라이언트가 연결 오류를 받았습니다. MVC를 거치면 스트림이 정상적으로 끝난 것처럼 닫혔습니다.
왜
응답이 이미 시작된 뒤 예외가 나면 Tomcat이 응답을 정상 종료합니다.
해결
Gateway 설정으로는 해결하지 못했습니다. 클라이언트가 done 이벤트를 받았을 때만 정상 완료로 판정하면 됩니다. 이 저장소의 React 클라이언트와 측정 스크립트는 이렇게 처리합니다.

WebFlux 6번: 첫 토큰이 10초보다 늦으면 504

무슨 일
첫 토큰이 12초 뒤에 나오는 스트림에서 WebFlux Gateway가 10초에 504를 반환했습니다.
왜
WebFlux의 response-timeout은 Backend의 응답 헤더가 올 때까지만 기다립니다. Backend는 첫 토큰과 함께 헤더를 보내므로, 이 값이 사실상 "첫 토큰 대기 제한"이 됩니다. 이 측정에서는 10초로 설정했습니다.
해결
response-timeout을 첫 토큰 최대 대기 시간보다 길게 잡거나, Backend가 헤더를 먼저 보내게 합니다. 스트림 본문에는 적용되지 않으므로 긴 스트림 자체에는 영향이 없습니다(4번 성공).

설정을 잘못하면 실패하는 항목

기본값이나 흔히 쓰는 설정으로 바꿨을 때 실패한 경우입니다. 운영 설정을 정할 때 피해야 합니다.

참고로 MVC + simple 클라이언트 + read-timeout=10s는 4번에 성공했습니다. simple의 read-timeout은 토큰 사이 대기 시간에만 적용되기 때문입니다.

결론과 권장 설정

  • MVC 유지 조건(이벤트 단위 전달, 목표 동시 연결·지연·취소 처리 충족, 낮은 운영 복잡도): MVC 기본은 7·11·12번 실패로 불충족입니다. tuned는 9번을 제외하고 충족하며, 9번은 클라이언트에서 보완됩니다. 운영 복잡도는 설정 몇 줄과 커넥션 풀 Bean 하나입니다.
  • WebFlux 전환 조건(연결 수가 늘 때 리소스 효율이나 지연이 유의미하게 개선): tuned 대비 WebFlux가 추가로 성공하는 항목은 9번 하나입니다. 500개 동시까지 지연과 리소스 차이도 작았습니다(부록 참고).

tuned 구성

  1. spring.http.client.factory=jetty. 7번 해결.
  2. spring.http.client.read-timeout을 서비스의 최대 스트림 길이 이상으로 설정합니다. Jetty는 이 값을 전체 시간 제한으로 쓰므로, 설정하지 않으면 10초에서 끊깁니다.
  3. Jetty maxConnectionsPerDestination을 목표 동시 스트림 수 이상으로 설정합니다(기본 64). 이 저장소에서는 poc.jetty-client.max-connections-per-destination입니다.
  4. spring.threads.virtual.enabled=true, 또는 server.tomcat.threads.max를 목표 동시 스트림 수 이상으로 설정합니다. 11·12번 해결.
  5. 클라이언트는 done 이벤트로 정상 완료를 판정합니다. 9번 보완.
  6. server.tomcat.accept-count를 동시에 몰릴 수 있는 연결 수 이상으로 설정합니다(기본 100, OS somaxconn 이하). Docker 재측정에서 발견했습니다.

WebFlux 전환을 다시 검토할 조건

  • 목표 동시 스트림이 500보다 훨씬 많아서, 별도 호스트에서 재측정했을 때 tuned가 실패하는 항목이 생길 때.
  • 9번(스트림 중간 오류를 연결 오류로 구분)이 반드시 필요할 때.
  • Jetty 클라이언트를 쓸 수 없는 제약이 생겼는데, Spring 업그레이드로 JDK 클라이언트의 drain 동작이 바뀌지 않았을 때. 저장소의 GatewayMvcJdkClientTest가 현재 동작을 고정하고 있어서, 동작이 바뀌면 이 테스트가 실패합니다.

재측정하면서 새로 확인한 것

  1. Tomcat 연결 대기열 넘침. 첫 실행에서 tuned가 12번에 실패했습니다(첫 토큰 p95 1.26초). 500건 중 26건만 약 1.26초에 몰려 있었고, /proc/net/netstat의 ListenOverflows가 MVC 컨테이너에서만 늘었습니다(tuned 172, 기본 62, WebFlux·Backend 0). Tomcat accept-count 기본값 100이 넘쳐서 버려진 SYN이 1초 뒤 재전송된 것입니다. tuned에 server.tomcat.accept-count: 1000을 추가하자 넘침이 0이 됐고 12번도 통과했습니다. 기본값 구성은 재시작 직후에는 매번 실패했지만, JVM이 데워진 뒤에는 통과하기도 해서 재현이 일정하지 않습니다. 그래서 자동 판정에는 넣지 않았습니다.
  2. 동시 연결 판정에 "최대 1초 이내"를 추가했습니다. p95만 보면 5% 미만의 요청이 1초 넘게 늦는 문제를 놓칩니다.
  3. 콜드 스타트 보정. 방금 재시작한 WebFlux가 12번에서 p95 705ms로 실패했는데, 이는 JIT 워밍업 문제였습니다. 짧은 워밍업을 넣고, 이후 모든 요청이 같은 시각에 연결하도록 출발 시점을 맞췄습니다.
  4. WebFlux 스트림 1건 정체 (원인 미확인). 한 실행에서 10번 중 1건이 토큰 8개 후 멈췄습니다. Backend는 10개를 모두 보내고 정상 종료했지만, 클라이언트는 나머지를 받지 못하고 18분 뒤 타임아웃됐습니다. 5회 다시 돌렸을 때는 재현되지 않았고, Gateway와 k6 클라이언트 중 어디서 멈췄는지는 확인하지 못했습니다. 이후 요청 타임아웃을 "스트림 길이 × 3 + 30초"로 줄였습니다.

T06클라이언트 중단 → Backend 취소

사용자가 답변 도중 "중단"을 누르거나 탭을 닫았을 때 Backend(LLM)가 토큰 생성을 언제 멈추는지를 쟀습니다.

  1. 클라이언트가 토큰 50개 × 200ms 간격(약 10초) 스트림을 요청합니다.
  2. 토큰 3개를 받은 순간 연결을 끊고 그 시각을 abortedAt으로 기록합니다.
  3. Backend는 스트림이 끝난 시각 finishedAt과 끝난 이유를 기록합니다. CANCELLED는 중간에 취소됨, COMPLETED는 50개를 끝까지 만들고 정상 종료됨입니다.
  4. 전파 시간 = finishedAt − abortedAt. 클라이언트와 Backend가 같은 머신이라 시계가 같습니다.
  5. 중단 후 생성된 토큰 = Backend가 생성한 토큰 수 − 3. 사용자가 받지 않을 토큰을 몇 개 더 만들었는지입니다.

Backend 직접, WebFlux: 즉시 취소

Netty는 이벤트 루프가 연결된 소켓을 계속 지켜봅니다. 클라이언트가 연결을 닫으면 바로 알아채고 스트림 구독을 취소합니다. WebFlux Gateway는 이때 Backend로 가는 연결도 즉시 닫고, Backend가 그것을 보고 취소합니다. 소켓 이벤트만으로 처리되므로 다음 토큰을 기다리지 않습니다.

MVC 기본: 취소되지 않음

while (Backend에서 읽기) {      ← 대부분의 시간을 여기서 대기
    클라이언트에 쓰기 + flush
}
  1. MVC Gateway는 요청마다 Tomcat 스레드 하나가 위 반복문을 돕니다. 클라이언트가 끊어도 스레드는 Backend 읽기에서 대기 중이라 바로 알 수 없습니다.
  2. 다음 토큰이 와서 클라이언트에 쓰려고 할 때 쓰기 실패 예외가 나며 비로소 끊긴 것을 압니다.
  3. 반복문을 빠져나오면서 Gateway가 Backend 응답을 close()합니다.
  4. Spring 6.2.11의 JdkClientHttpResponse.close()는 커넥션 재사용을 위해 남은 본문을 끝까지 읽습니다(drain). simple, HttpComponents, Reactor 클라이언트도 같습니다.
  5. 그래서 Gateway가 Backend 스트림을 마지막까지 읽고, Backend는 클라이언트가 떠난 줄 모르고 정상 완료합니다.

결과적으로 사용자가 보지 않을 토큰의 비용이 끝까지 나가고, 그동안 Tomcat 스레드와 Backend 연결이 하나씩 묶입니다. 정상 완료로 끝나므로 Backend 로그와 지표로는 중단을 알 수 없습니다.

MVC + Jetty, tuned: 200~400ms 후 취소

Jetty 클라이언트의 close()는 drain하지 않고 바로 닫으므로 Backend가 취소됩니다. 0ms가 아닌 이유는 위 1~2단계 때문입니다. MVC는 다음 토큰을 쓸 때만 단절을 알 수 있습니다. 끊긴 직후의 첫 쓰기는 OS 송신 버퍼에 들어가며 성공할 수 있고, 클라이언트 쪽 OS가 RST로 응답한 뒤 두 번째 쓰기에서 실패합니다. 그래서 토큰 간격(200ms)의 1~2배가 걸리고(p50 204ms = 1간격, p95 410ms = 2간격), 그 사이 Backend가 토큰 1~2개를 더 만듭니다.

  • 단, MVC의 감지 시간은 다음 토큰까지의 간격에 비례합니다. 모델이 첫 토큰 전에 30초 동안 생각하는 중에 사용자가 중단하면, MVC는 최대 30초 뒤에야 알아채고 그동안 Backend는 계속 작업합니다. WebFlux는 이 경우에도 즉시 압니다.
  • MVC 기본 설정을 그대로 운영하는 것은 피해야 합니다.

T12압축과 앞단 프록시

Tomcat과 Reactor Netty의 gzip은 flush마다 sync-flush를 해서 이벤트 단위 전달이 유지됐습니다(lag p95 2~4ms). nginx 1.27은 기본값, proxy_buffering on 강제, gzip 모두에서 이벤트를 받는 대로 넘겼습니다(lag p95 16ms 이하, Docker 네트워크 포함). 버퍼링은 클라이언트가 느릴 때 드러나는데, 이 측정에서는 재현되지 않았습니다.

MVC tuned는 나중에 따로 측정했으므로 같은 시점의 tuned 단독 값과 비교해야 합니다. 이때는 서버 4개와 nginx 컨테이너가 동시에 떠 있어서 lag가 전반적으로 높습니다. 모든 경우 1.1초 안에 토큰 5개가 도착하는 점진 전달 검사를 통과했습니다.
